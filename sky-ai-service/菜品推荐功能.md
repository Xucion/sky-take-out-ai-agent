我会把这个功能设计成“LLM 理解需求，业务服务负责筛选和排序，LLM 只解释推荐结果”。不能让模型直接读取所有菜品后凭感觉推荐。

## 一、Agent 链路

```
用户：“想吃点微辣的，30 元以内，不要甜口”
        ↓
偏好槽位抽取
        ↓
{
  maxPrice: 30,
  spicyLevel: 2,
  excludedTags: ["甜"],
  preferredTags: ["微辣"]
}
        ↓
调用 recommend_dishes 工具
        ↓
业务服务过滤并排序候选菜品
        ↓
返回 Top 3～5
        ↓
Agent 解释推荐理由
```

当用户明确提供“整顿饭总预算 + 用餐人数”时，链路改为调用
`recommend_meal_combo`，由业务服务确定性搭配主菜、蔬菜、汤和主食，并复核数量、总价和剩余预算。

模型负责：

- 理解自然语言；
- 补全多轮偏好；
- 必要时追问；
- 将推荐结果组织成人类可读回答。

业务服务负责：

- 价格过滤；
- 口味匹配；
- 起售状态检查；
- 过敏原等硬性排除；
- 推荐评分和排序。

## 二、现有数据需要扩展

当前 `dish` 已经有价格、分类、描述和起售状态；`dish_flavor` 保存的是“温度、辣度”等可选规格，不等同于可用于推荐的标准化菜品标签。

建议增加菜品画像表：

```
CREATE TABLE dish_profile (
    dish_id          BIGINT PRIMARY KEY,
    spicy_level      TINYINT NOT NULL DEFAULT 0,
    sweetness_level  TINYINT NOT NULL DEFAULT 0,
    saltiness_level  TINYINT NOT NULL DEFAULT 0,
    oiliness_level   TINYINT NOT NULL DEFAULT 0,
    calorie_level    TINYINT,
    tags             JSON,
    allergens        JSON,
    update_time      DATETIME NOT NULL
);
```

示例：

```
{
  "dishId": 101,
  "spicyLevel": 2,
  "sweetnessLevel": 0,
  "oilinessLevel": 2,
  "tags": ["川味", "下饭", "肉类"],
  "allergens": ["花生"]
}
```

如果后续还要推荐套餐，可以抽象成统一表：

```
catalog_item_profile
- item_type：DISH / SETMEAL
- item_id
- 各种口味和标签
```

## 三、结构化偏好上下文

推荐需求不能只保存在聊天文本里，建议维护结构化状态：

```
public record RecommendationContext(
    BigDecimal minPrice,
    BigDecimal maxPrice,
    Integer peopleCount,
    Integer spicyLevelMin,
    Integer spicyLevelMax,
    Integer sweetnessLevelMax,
    List<String> preferredTags,
    List<String> excludedTags,
    List<String> allergens,
    Long categoryId
) {}
```

Redis 中可以保存为：

```
Key: ai:ctx:{conversationId}:recommendation
```

```
{
  "maxPrice": 30,
  "spicyLevelMin": 1,
  "spicyLevelMax": 2,
  "preferredTags": ["下饭"],
  "excludedTags": ["甜"],
  "allergens": ["花生"],
  "updatedSequence": 18
}
```

多轮对话可以增量更新：

```
用户：想吃辣的
→ spicyLevelMin = 2

用户：别太辣
→ spicyLevelMax = 3

用户：控制在30以内
→ maxPrice = 30

用户：算了，今天不想吃辣
→ spicyLevelMin = 0
→ spicyLevelMax = 0
```

当前会话偏好应该有 TTL。长期口味偏好应单独保存，并且最好经过用户明确授权，不能把一次聊天中的需求永久当作用户画像。

## 四、Agent 意图和工具

新增意图：

```
DISH_RECOMMENDATION
```

新增受控工具：

```
recommend_dishes
```

工具参数必须是结构化字段：

```
{
  "minPrice": 10,
  "maxPrice": 30,
  "spicyLevelMin": 1,
  "spicyLevelMax": 2,
  "preferredTags": ["下饭", "肉类"],
  "excludedTags": ["甜"],
  "allergens": ["花生"],
  "limit": 5
}
```

不要把用户原始描述直接传给数据库，也不要允许模型传 SQL、排序表达式或 `userId`。

内部接口可以设计为：

```
POST /internal/ai-tools/catalog/dish-recommendations
Authorization: Bearer <service-token>
X-AI-User-Context: <context-token>
```

返回内容控制在推荐需要的字段：

```
{
  "items": [
    {
      "dishId": 101,
      "name": "宫保鸡丁",
      "price": 28,
      "matchedTags": ["微辣", "下饭"],
      "flavorOptions": ["不辣", "微辣", "中辣"],
      "reasonCodes": ["PRICE_MATCH", "SPICY_MATCH"]
    }
  ]
}
```

推荐理由最好由业务服务返回标准原因码，模型再转换成自然语言，避免模型编造：

> 宫保鸡丁 28 元，在你的预算内，可以选择微辣，而且比较下饭。

## 五、筛选与排序

先执行硬性过滤：

```
status = 起售
price 在预算范围内
排除明确不喜欢的标签
排除过敏原
满足分类等必要条件
```

然后对候选菜品评分：

```
总分 =
  口味匹配度 × 40%
+ 价格匹配度 × 25%
+ 用户历史偏好 × 15%
+ 销量或热度 × 10%
+ 多样性 × 10%
```

例如：

```
score =
    tasteScore * 0.40
  + priceScore * 0.25
  + preferenceScore * 0.15
  + popularityScore * 0.10
  + diversityScore * 0.10;
```

需要注意：

- 过敏原属于硬约束，不能参与软评分；
- 预算超出也应直接排除，除非用户允许“稍微超一点”；
- 推荐列表要保持多样性，避免全部是同一分类；
- 销量可以从 `order_detail` 聚合，但建议生成独立的菜品热度统计，不要每次实时扫描订单。

## 六、什么时候需要追问

这些情况不应直接猜：

- “预算 50”但不知道是一人还是多人；
- “清淡一点”但用户还要求重辣；
- 明确提到严重过敏，但菜品过敏原数据缺失；
- 条件过严导致没有候选。

例如：

> 50 元是单个菜品预算，还是这顿饭的总预算？

如果没有完全匹配项，应该明确放宽了什么条件：

> 30 元以内没有同时满足“微辣、无花生、低油”的菜品。要不要把预算提高到 35 元，或者放宽低油要求？

## 七、缓存设计

Redis 可以缓存两类数据：

```
ai:ctx:{conversationId}:recommendation
```

保存当前会话的推荐条件。

```
ai:catalog:dish:{dishId}
ai:catalog:index:tag:{tag}
ai:catalog:index:price:{range}
```

保存菜品画像和检索索引。

菜品上下架、价格或画像改变时删除相关缓存。最终推荐前仍需要确认菜品当前起售状态和实际价格，避免返回过期信息。

## 八、推荐落地顺序

MVP 可以先实现：

1. 管理端为菜品配置辣度、甜度、标签和过敏原；
2. Agent 抽取价格、辣度、偏好和排除条件；
3. 新增 `recommend_dishes` 工具；
4. 使用确定性 SQL 过滤和简单加权排序；
5. Redis 保存本次会话的结构化推荐条件；
6. Agent 返回 3～5 个菜品及可验证的推荐理由。

第二阶段再加入：

- 用户历史购买偏好；
- 销量和热门程度；
- 长期用户画像；
- 协同过滤或向量召回；
- 基于销量和历史偏好的多人组合进一步优化。

对当前项目来说，第一版没必要直接上向量数据库。菜品数量有限且需求主要是价格、辣度、标签等结构化条件，用 SQL/Redis 过滤加确定性评分会更准确、可解释，也更容易测试。

## 九、MVP 实现状态

当前版本已经完成第一阶段闭环：

- 管理端菜品新增/编辑页可以维护辣度、甜度、咸度、油腻程度、标签和过敏原；
- `sql/dish-recommendation-migration.sql` 提供 `dish_profile` 建表脚本；
- `sky-server` 提供经过双 JWT 保护的 `POST /internal/ai-tools/catalog/dish-recommendations`；
- 推荐服务执行起售、价格、分类、排除标签、最高甜度和过敏原硬过滤；
- 候选结果按辣度、标签、价格和分类多样性确定性排序，并返回原因码；
- `sky-ai-service` 新增 `DISH_RECOMMENDATION` 意图和 `recommend_dishes` 受控工具；
- 会话偏好优先保存到 Redis，默认 TTL 为 30 分钟，Redis 故障时仅临时降级到进程内缓存；
- 预算口径不明确或清淡与重辣冲突时会先追问，不会让模型自行猜测；
- 预算澄清状态会随会话保存，“2人”“人均100”等短回答能够继续原推荐流程；
- 已新增 `POST /internal/ai-tools/catalog/meal-combinations` 和 `recommend_meal_combo`；确认总预算与人数后，业务服务按画像和安全约束生成不超预算的多人组合；
- 组合推荐仅要求主菜满足辣度，蔬菜、汤和主食不会因为“不辣”被错误排除，并返回数量、小计、总价和剩余预算。

用户历史偏好、销量热度、长期画像、组合全局最优和向量召回仍属于第二阶段范围。
