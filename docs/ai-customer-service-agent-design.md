# 苍穹外卖用户端智能客服 AI Agent 设计方案

> 文档状态：方案草案（不包含代码改动）  
> 调研与项目核对日期：2026-08-19  
> 目标读者：产品、后端、前端、测试、运维人员

## 1. 结论先行

本项目适合从一个“受控的单 Agent 智能客服”开始，而不是直接建设能够自由规划和执行任意操作的多 Agent 系统。

首个可上线版本应完成三件事：

1. 基于经过审核的知识回答配送范围、营业时间、餐具、支付、取消规则等常见问题；
2. 在用户登录后，通过只读工具查询实时的店铺、菜品和本人订单信息；
3. 不确定、敏感、用户明确要求人工或连续未解决时，携带对话摘要和已收集信息转人工。

推荐将 AI 能力放在仓库内的独立 `sky-ai-service` 中，以独立进程运行，通过内部 API 读取 `sky-server` 的业务数据。主要原因是当前业务服务使用 Spring Boot 2.7.3，Maven 编译目标为 Java 9，而当前主流 Java AI 框架面向更新的 Spring Boot/Java 运行时。独立服务可以避免为了试点 AI 而立即迁移整个交易内核，也便于单独限流、降级、扩容和替换模型。

推荐技术方向：

- Agent 编排：Spring AI 的稳定版能力，采用 Chat Client、RAG、Tool Calling 和可观测性，不采用实验性的自由多 Agent；
- AI 服务运行时：Java 17 或 21 LTS；Spring Boot 与 Spring AI 使用官方兼容矩阵中的同一代稳定版本。以当前文档为例，Spring AI 2.0.x 对应 Spring Boot 4.0.x/4.1.x，实施时必须再次锁定兼容版本，不能把版本写成浮动依赖；
- 大模型接入：使用 OpenAI-compatible Provider Adapter，国内部署首选阿里云百炼/Qwen 作为第一候选，但业务代码不能写死供应商；
- 知识检索：独立向量库 Qdrant（开发和中小规模首选）+ MySQL 中的知识元数据；已有普通 Redis 继续承担缓存、限流和短期会话状态，不能默认它已经具备向量检索能力；
- 用户端流式响应：HTTP SSE；会话状态及人工接管事件可在后续使用鉴权后的 WebSocket。不要复用当前广播式 `/ws/{sid}` 作为客服聊天通道；
- 对话记录、工单和审计：MySQL；短期上下文与幂等控制：Redis；
- 观测：Micrometer/OpenTelemetry，记录耗时、首字延迟、Token、工具调用、检索命中、升级人工及业务结果，默认不记录完整敏感提示词。

## 2. 当前项目基线

### 2.1 已有能力

根据仓库现状，项目并非只有一个纯 Java 内核，而是已经具备可承接客服入口和业务工具的前后端基础：

- 后端：Maven 多模块，包含 `sky-common`、`sky-pojo`、`sky-server`；
- 运行框架：Spring Boot 2.7.3、Spring MVC、MyBatis、MySQL、Redis；
- 用户身份：用户端 JWT，后端拦截 `/user/**` 并将登录用户作为业务上下文；
- 用户业务：店铺状态、分类、菜品、套餐、购物车、地址、下单、支付、订单详情、取消、再来一单、催单；
- 用户前端：`sky-web-user`，Vue 3 + TypeScript + Pinia + Axios；
- 实时基础：后端已有 WebSocket，但当前实现是静态 `Map` 保存连接并向全部客户端广播，适用于原有来单/催单通知，不满足客服会话的用户隔离、鉴权、断线恢复和多实例路由要求。

### 2.2 对 AI 接入有影响的现状

| 现状 | 影响 | 方案中的处理 |
| --- | --- | --- |
| 业务服务为 Spring Boot 2.7.3，编译目标 Java 9 | 不能直接照搬当前 Spring AI 示例 | AI 服务独立运行在 Java 17/21；交易内核暂不升级 |
| 所有 `/user/**` 除少数接口外均要求 JWT | Agent 工具必须继承用户身份 | 登录用户 ID 由服务端上下文注入，不允许模型传入或改写 |
| 已有菜品、订单等 Service/Mapper | 可快速形成客服工具 | 在 `sky-server` 增加专用内部只读门面，而非 Agent 直连业务表 |
| 已有 Redis | 可做限流、短期记忆和幂等 | 向量检索另用专用向量库；除非明确部署 Redis Stack/Vector Search |
| 没有客服坐席、工单和知识管理模块 | “转人工”目前没有真正接收方 | MVP 可先生成待处理客服单，之后补管理端坐席收件箱 |
| 订单取消、支付、退款会改变资金或状态 | 模型误操作风险高 | 首期不向 Agent 暴露写工具；后续必须二次确认和代码级校验 |

## 3. 现有智能客服产品的共同做法

本方案优先参考了 Zendesk AI Agents、Intercom Fin、Salesforce Agentforce，以及 Java AI 框架和安全社区的官方资料。它们的产品命名不同，但底层做法高度一致。

### 3.1 用“已批准知识”约束回答

Intercom 说明 Fin 会理解问题、检索支持内容和数据，再基于这些来源作答，并支持按受众控制文章可见性。Zendesk 在自动解决问题的配置中要求至少连接一个知识源。由此可见，生产客服不应只依赖模型训练时的通用知识，而要使用可审核、可发布、可失效的业务知识。

对本项目的启示：菜单价格、库存、订单状态属于实时结构化数据，应通过工具查询；配送政策、取消规则、常见问题属于知识库，应通过 RAG 检索。二者不能混在一批静态文档中。

### 3.2 Agent 要能调用业务工具，但工具执行权在应用端

Zendesk 提供连接业务系统、工作流和 API 的能力；Salesforce 将客服 Agent 归纳为主题/指令、动作和护栏；Spring AI 与阿里云百炼的官方说明也都强调，大模型只生成工具调用请求，实际工具由应用执行。

对本项目的启示：模型可以决定“需要查订单”，但应用必须在执行前校验登录状态、订单归属、参数格式、调用次数和工具权限。模型永远不能获得数据库凭证，也不能把用户输入直接拼成 SQL。

### 3.3 转人工是主流程，不是失败兜底

Intercom 支持根据明确请求、负面情绪、重复对话、敏感主题、结构化用户属性等条件转人工，并可在移交前收集信息；Zendesk 支持携带完整上下文升级；Salesforce 也将升级规则和完整上下文交接作为客服 Agent 的标准组成。

对本项目的启示：必须从第一版就设计人工接管状态机、路由原因、摘要和接管后的 Bot 停止条件，即使第一阶段只有简化的工单队列。

### 3.4 可解释、可评估、可运营

成熟产品能查看答案使用了哪些来源、因何升级、最终是否解决。OpenTelemetry 的 GenAI 语义约定覆盖 Token 用量、调用耗时和首 Token 时间等指标。

对本项目的启示：不能只记录“接口成功”。需要能回答：哪个意图最常见、检索到了什么、模型调用了什么工具、为何转人工、用户是否再次追问、一次解决率和每次解决成本是多少。

### 3.5 护栏必须在代码层生效

OWASP 将 Prompt Injection 和 Excessive Agency（权限过大）列为 LLM 应用的重要风险。自然语言提示词可以表达规则，但不能代替鉴权、参数校验、权限白名单、确认流程和审计。

## 4. 产品功能设计

### 4.1 用户入口

在 `sky-web-user` 增加独立的“客服”入口和会话页，入口可放在底部导航或个人中心。首屏提供：

- 明确标识“AI 客服”，避免冒充人工；
- 常用问题快捷入口：营业时间、配送范围、订单进度、如何取消、催单；
- 当前是否有人工客服可接入及预计响应说明；
- 隐私提示：不要发送银行卡号、密码、验证码等敏感信息。

用户消息采用 SSE 流式返回。SSE 比 WebSocket 更适合首期的“客户端发一个 HTTP 请求、服务端持续返回文本和事件”的单向流式场景，实现和代理配置也更简单。

### 4.2 P0：首个可用版本

#### 知识问答

- 营业时间、店铺状态说明；
- 配送范围、配送费和预计时效规则；
- 支付、取消、退款的一般规则；
- 餐具、打包、发票等规则（以项目实际业务为准）；
- 菜品的一般介绍；涉及过敏原时只引用经过审核的结构化信息，否则明确无法确认并转人工。

每个知识答案保存内部来源 ID、知识版本和检索分数。前台可用“依据：配送规则”这样的简短来源标签，而不是暴露内部 Prompt。

#### 实时查询

- 查询当前店铺是否营业；
- 根据名称、分类、价格范围查询在售菜品/套餐；
- 查询用户本人的最近订单；
- 查询用户本人的某笔订单状态、金额、下单时间、预计送达时间；
- 给出订单状态含义和下一步建议；
- 生成“催单”或“取消订单”的操作指引，但 P0 不替用户实际执行。

#### 澄清和导航

- “我的订单怎么还没到”若有多笔进行中订单，先让用户选择；
- “想吃辣的，30 元以内”转为结构化菜品检索；
- 返回可点击的菜品、订单详情或操作页链接；
- 无法确定意图时只问一个最必要的澄清问题，不连续盘问。

#### 转人工/工单

触发条件至少包括：

- 用户明确要求人工；
- 涉及食品安全、过敏反应、投诉、疑似欺诈或人身安全；
- 涉及异常扣款、退款争议、订单归属异常；
- 知识检索无可靠来源，或工具返回异常；
- 同一问题连续两次未解决，或检测到明显负面情绪；
- Agent 请求未授权工具或越权数据；
- 服务端规则命中 VIP、高金额订单等需要人工处理的条件。

移交内容包括：用户 ID、会话 ID、问题分类、关联订单、用户原话、已查询结果、AI 尝试、升级原因、自动摘要和紧急程度。人工接管后 Bot 必须停止回复，除非坐席明确交还。

### 4.3 P1：确认后执行的助手

在 P0 指标达标后逐项开放：

- 将选定菜品加入购物车；
- “再来一单”前展示缺货、价格变化和购物车差异；
- 发起催单；
- 修改可安全变更的信息；
- 取消满足业务规则的订单。

每个写操作都必须满足：向用户展示明确的操作预览、用户点击确认、服务端重新鉴权和校验、幂等键、防重放、完整审计。退款、支付、补偿、修改收款信息等资金动作不建议交给自治 Agent；可以由 Agent 收集信息后转人工或进入确定性审批流。

### 4.4 P2：客服运营和主动服务

- 管理端人工坐席收件箱、接管和转派；
- AI 生成会话摘要、意图标签和建议回复；
- 从高频未解决问题发现知识缺口，但只能生成知识草稿，不能自动发布；
- 在订单异常、配送延迟等确定性业务事件触发时主动通知；
- 多渠道接入（Web、小程序等）共用同一会话和权限模型。

## 5. 总体架构

```text
sky-web-user / mp-weixin
        |
        | JWT + HTTPS；POST message / SSE stream
        v
sky-ai-service（Java 17/21，独立进程）
  ├─ Chat API 与会话状态机
  ├─ 意图/风险路由与确定性护栏
  ├─ RAG 检索与来源管理
  ├─ Agent 编排与模型 Provider Adapter
  ├─ Tool Registry（首期只读）
  ├─ 转人工/工单适配器
  └─ 日志、评估、限流、降级
        |                    |
        | 内部鉴权 API        | OpenAI-compatible API
        v                    v
sky-server               Qwen / 可替换模型
  ├─ 订单只读门面
  ├─ 菜品只读门面
  └─ 店铺只读门面
        |
        v
 MySQL / Redis       Qdrant + 知识元数据
```

### 5.1 为什么不让 Agent 直连 Mapper 或数据库

- 会绕过现有 Service 的业务约束和用户隔离；
- 表结构变化会直接破坏工具契约；
- 无法为不同工具独立授权、限流和审计；
- 容易把数据库错误、内部字段或其他用户信息暴露给模型。

正确方式是在 `sky-server` 形成窄而稳定的内部客服门面。门面返回专用 DTO，只暴露回答问题所需字段。

### 5.2 为什么不直接复用现有 WebSocket

当前 `/ws/{sid}` 的 `sid` 由路径传入，没有看到客服级连接鉴权；连接保存在单机静态 `HashMap`，且 `sendToAllClient` 会广播全部会话。它不具备多实例共享、按会话路由、消息确认、断线游标和人工接管状态。因此首期文本生成用 SSE，后续若实现坐席双向聊天，再建设带 JWT、会话归属校验和分布式消息总线的专用通道。

### 5.3 核心请求流程

1. 前端携带 JWT 和 `conversationId` 发送消息；
2. AI 服务完成频率、长度、内容风险和会话状态检查；
3. 服务端从认证上下文取得 `userId`，绝不从模型工具参数取用户身份；
4. 路由层判断是知识问题、实时查询、澄清、升级人工还是拒答；
5. 知识问题执行混合检索；实时问题由模型请求白名单工具；
6. 应用校验工具名和参数后调用 `sky-server` 内部门面；
7. 模型仅基于工具结果/可靠知识生成简洁回复；
8. 输出过滤器检查敏感数据、来源和禁止承诺；
9. SSE 返回文本片段、来源、工具结果卡片和最终状态；
10. 保存消息、工具审计、Token、时延和用户反馈。

## 6. Agent 设计：受控工作流优先

### 6.1 Agent 边界

模型负责：

- 理解自然语言和上下文；
- 选择允许的只读工具；
- 生成检索查询；
- 组织自然、友好的回答；
- 对交接信息生成摘要。

代码负责：

- 身份、权限和资源归属；
- 是否允许执行动作；
- 业务规则、金额计算和状态转换；
- 高风险升级与强制拒答；
- 幂等、限流、超时、重试和熔断；
- 会话状态和人工/Bot 控制权。

不建议让模型自行决定“置信度足够所以可以退款”或“这个订单应该取消”。模型的自信程度不是可靠的授权信号。

### 6.2 初始工具清单

| 工具 | 输入 | 输出 | P0 权限 |
| --- | --- | --- | --- |
| `get_shop_status` | 无 | 营业状态、时间说明 | 公开只读 |
| `search_menu` | 关键词、分类、价格范围、口味 | 在售商品精简信息 | 登录只读 |
| `get_recent_orders` | 状态、数量上限 | 当前用户订单摘要 | 登录且仅本人 |
| `get_order_detail` | 订单 ID | 当前用户订单详情 | 登录且仅本人 |
| `get_order_progress` | 订单 ID | 状态、预计时间、可用操作 | 登录且仅本人 |
| `create_handoff` | 原因、关联订单、摘要 | 工单号/排队状态 | 受控写入 |

`create_handoff` 只创建客服记录，不改变订单。订单 ID 可以由模型选择，但用户 ID 必须由可信服务端上下文注入；工具响应应做字段白名单和长度限制。

### 6.3 会话状态机

```text
BOT_ACTIVE
  ├─ 已解决/用户结束 ──> RESOLVED
  ├─ 命中升级规则 ────> WAITING_HUMAN
  └─ 系统异常 ────────> DEGRADED

WAITING_HUMAN
  ├─ 坐席接管 ────────> HUMAN_ACTIVE
  └─ 用户取消等待 ────> BOT_ACTIVE（按策略）

HUMAN_ACTIVE
  ├─ 坐席解决 ────────> RESOLVED
  └─ 坐席交还 Bot ────> BOT_ACTIVE
```

只有状态机能切换回复方。不能仅靠 Prompt 告诉 Bot“人工接管后不要回复”，否则异步消息可能造成 Bot 和人工同时回复。

## 7. RAG 知识库设计

### 7.1 知识源分层

| 数据 | 来源 | 获取方式 | 更新策略 |
| --- | --- | --- | --- |
| 退款、取消、配送、食品安全规则 | 审核后的客服知识文档 | RAG | 发布即增量重建索引 |
| 营业状态 | `sky-server` | 工具 | 实时 |
| 菜品价格、上下架、口味 | `sky-server` | 工具 | 实时，必要时短缓存 |
| 订单状态和用户信息 | `sky-server` | 工具 | 实时、按用户鉴权 |
| 历史优秀客服话术 | 脱敏后人工筛选 | 仅用于风格/评测 | 不直接作为事实来源 |

### 7.2 知识记录字段

每个知识条目至少包含：`documentId`、标题、正文、业务分类、适用渠道、适用人群、版本、状态、责任人、生效/失效时间、更新时间、来源 URL/文件、敏感等级。

只有 `PUBLISHED` 且在有效期内的内容进入生产检索。变更必须保留版本，旧向量必须可删除，防止新旧政策同时被召回。

### 7.3 检索流程

1. 规范化用户问题，并结合最近必要上下文改写检索词；
2. 先按状态、渠道、时间、用户范围等元数据过滤；
3. 向量检索与关键词检索并行，合并结果；
4. 可选重排序；
5. 达不到阈值时不强答，转澄清或人工；
6. 将少量高相关片段、标题和版本提供给模型；
7. 输出保存来源引用，供审计和用户查看。

中文知识切分要按标题、段落和规则项进行，不应只按固定字符数暴力切片。价格、日期、范围、条件和例外必须尽量处于同一片段。

## 8. 模型与框架选型

### 8.1 Java Agent 框架

| 选项 | 优点 | 风险/成本 | 结论 |
| --- | --- | --- | --- |
| Spring AI | 与 Spring、配置、Micrometer 体系一致；具备 Tool Calling、RAG、模型抽象和观测 | 当前代版本不兼容本项目 Boot 2.7/Java 9；需独立服务或整体升级 | 推荐，放入独立 AI 服务 |
| LangChain4j | Java 原生；AI Services、Memory、RAG 和 Tools 完整；模型适配丰富 | Agentic 模块官方仍标注实验性；与 Spring 版本也需核对 | 合理备选，只用稳定核心，不依赖实验 Agentic API |
| 直接调用模型 HTTP API | 依赖最少、协议清晰 | 需自行实现流式解析、工具循环、记忆、观测和 Provider 差异 | 适合短期 PoC，不建议成为长期客服平台内核 |

Spring AI 官方文档明确指出：工具调用时模型只提出调用请求，应用负责执行；这正符合本方案的安全边界。选型时不追求“Agent”名词，而应优先成熟的 Chat、RAG、Tools 和工作流组合。

### 8.2 模型 Provider

国内部署可首先评测阿里云百炼的 Qwen 模型。百炼提供 OpenAI-compatible API、工具调用及 Embedding，便于通过 `baseUrl + apiKey + model` 配置切换。模型名变化较快，方案阶段不写死具体型号；上线前使用固定评测集比较至少一档效果模型和一档低成本模型，再锁定快照/版本。

Provider Adapter 至少统一：

- 流式与非流式聊天；
- 工具调用和结构化输出；
- Embedding；
- 超时、重试、错误码、Token 用量；
- 内容安全结果；
- 模型、地域和数据保留配置。

不能假设“OpenAI-compatible”代表所有字段和行为完全一致，供应商官方也明确说明兼容接口存在参数差异，因此需要契约测试。

### 8.3 模型分工

- 主对话模型：意图理解、工具选择、回答生成；
- Embedding 模型：中文知识向量化，文档和查询必须用同一模型/维度；
- 可选轻量模型：意图分类、摘要、风险标签，以降低成本；
- 不建议首期加入多 Agent 模型互相调用，会增加延迟、Token、调试难度和错误传播。

## 9. API 与数据设计草案

### 9.1 对外 API

| API | 作用 |
| --- | --- |
| `POST /user/ai/conversations` | 新建会话 |
| `GET /user/ai/conversations/{id}` | 获取会话及当前控制状态 |
| `GET /user/ai/conversations/{id}/messages` | 分页拉取历史消息 |
| `POST /user/ai/conversations/{id}/messages` | 发送消息，响应为 SSE 事件流 |
| `POST /user/ai/conversations/{id}/feedback` | 点赞/点踩、是否解决及原因 |
| `POST /user/ai/conversations/{id}/handoff` | 用户主动申请人工 |

SSE 事件建议统一为：`message.delta`、`message.completed`、`source`、`card`、`handoff`、`error`。客户端收到重复事件时用 `eventId` 去重，并支持携带 `Last-Event-ID` 恢复。

### 9.2 核心表

- `ai_conversation`：用户、渠道、状态、当前处理方、关联订单、开始/结束时间；
- `ai_message`：角色、原文、展示内容、Token、模型、耗时、状态；
- `ai_tool_call`：工具、脱敏参数摘要、结果码、耗时、幂等键、审批信息；
- `ai_handoff`：原因、优先级、摘要、队列、接管人、时间；
- `ai_feedback`：是否解决、赞踩、原因、后续是否再次联系；
- `ai_knowledge_document` / `ai_knowledge_version`：知识元数据、版本和发布状态；
- `ai_eval_case` / `ai_eval_run`：固定评测问题、期望行为和每次模型/Prompt 的结果。

完整用户可见历史必须保存在数据库中；发送给模型的“记忆”只应是最近窗口加摘要。LangChain4j 官方也区分了 history 和 memory，不能把内存窗口当作合规的聊天记录。

## 10. 安全、隐私与可靠性

### 10.1 身份和权限

- AI 服务不能信任请求体中的 `userId`；
- `conversationId` 必须校验归属；
- 查询订单必须在 `sky-server` 再次校验订单属于当前用户；
- 内部 API 使用服务身份，并携带不可伪造的用户上下文；
- 每个工具独立定义权限、参数 Schema、超时和最大返回量；
- 管理端知识和坐席接口与用户接口隔离。

### 10.2 Prompt Injection 防护

- 把用户文本、检索文档、工具结果都视为不可信数据；
- 系统指令与不可信内容结构化分隔；
- 检索文档中出现“忽略之前指令”等内容不能获得更高权限；
- 工具采用白名单，模型不能动态提供 URL、类名、SQL 或脚本；
- 工具参数使用强类型 Schema 和枚举，执行前后都校验；
- 限制单轮工具次数、Agent 循环次数、总 Token 和总耗时；
- 检测到越权、提示词窃取、批量数据请求时拒绝并审计。

### 10.3 隐私与日志

- API Key 只放在密钥管理或环境变量中，不提交仓库；
- 手机号、地址、姓名、订单备注在发往模型前按“回答必需”最小化；
- 日志默认不保存完整 Prompt、工具参数和响应正文；
- 观测平台记录内容前必须脱敏；
- 为对话记录设置保留期、删除机制和访问审计；
- 在选定云模型的地域、数据保留和训练使用政策确认后再上线。

### 10.4 降级策略

- 模型超时：返回固定提示和常见问题入口，不无限重试；
- RAG 无结果：澄清或转人工，禁止凭常识编造政策；
- 业务工具失败：说明暂时无法查询并给出订单详情页链接；
- 向量库不可用：降级到经过审核的关键词检索；
- AI 服务不可用：用户端仍可正常浏览、下单和管理订单；
- 达到预算/并发上限：限流并提供人工/自助入口。

## 11. 评测与验收

### 11.1 上线前离线评测集

至少准备 200 条来自真实业务表达的脱敏问题，覆盖：

- 常见知识问答及同义表达；
- 多轮追问和指代；
- 菜品、订单实时查询；
- 不存在的订单、越权订单和未登录；
- 取消、退款、过敏原等高风险问题；
- Prompt Injection、诱导泄露系统提示、索取其他用户数据；
- 知识缺失、冲突、过期和工具超时；
- 必须转人工和不应转人工的边界。

每条用例定义：期望意图、允许工具、禁止工具、是否必须引用、是否必须转人工、事实要点和不可出现内容。模型或 Prompt 每次变更都运行回归。

### 11.2 核心指标

| 维度 | 指标 |
| --- | --- |
| 业务效果 | 自助解决率、转人工率、重复咨询率、工单重开率、用户满意度 |
| 准确性 | 有来源回答率、事实正确率、无依据回答率、工具选择/参数正确率 |
| 安全 | 越权读取率、未确认写操作率、敏感信息泄露率、注入攻击成功率 |
| 性能 | 首字延迟 P50/P95、完整响应 P95、工具耗时、错误率、超时率 |
| 成本 | 每会话/每解决 Token、模型费用、Embedding 与向量存储费用 |
| 运营 | 各意图解决率、升级原因、知识缺口、人工平均处理时间 |

初期不要只看“AI 回复率”。一个客服可以回复很多内容但没有解决问题。更重要的是“经确认解决且短期没有因同一问题再次联系”。

### 11.3 上线门槛建议

- 高风险场景必须转人工/拒答，测试通过率 100%；
- 跨用户订单访问测试通过率 100%；
- 未经确认的写操作为 0；
- 固定评测集事实正确率和工具参数正确率达到团队约定阈值；
- 灰度期间抽检全部高风险会话和一定比例的普通会话；
- 支持一键停用 AI，只保留人工或自助入口。

## 12. 分阶段实施路线

### 阶段 0：需求和数据准备（约 3～5 天）

- 确定客服负责人与真正的人工接收方；
- 整理前 50～100 个问题、标准答案、规则责任人和有效期；
- 从代码与业务确认订单状态、取消和退款规则；
- 建立首批评测集；
- 确认模型地域、预算、数据合规和人工服务时段。

退出条件：知识有明确责任人，人工升级不是“发到无人处理的队列”。

### 阶段 1：只读 PoC（约 1 周）

- 建立独立 AI 服务骨架和 Provider Adapter；
- 接入模型流式响应；
- 实现一个知识检索链路；
- 实现店铺状态、订单状态两个只读工具；
- 离线运行评测，不对真实用户开放。

退出条件：能够稳定复现、查看来源和工具轨迹，越权测试全部通过。

### 阶段 2：用户端 MVP（约 1～2 周）

- 客服页、SSE、会话历史和反馈；
- 完整 P0 工具、状态机和简化工单；
- 监控、限流、降级和内容脱敏；
- 先对白名单账号开放，再按比例灰度。

退出条件：高风险门槛达标，故障不影响下单主链路，人工能够接收到完整上下文。

### 阶段 3：人工坐席与运营闭环（约 1～2 周）

- 管理端会话列表、接管、回复、转派和关闭；
- 知识草稿、审核、发布、失效和重建索引；
- 会话抽检、意图报表、知识缺口和成本报表。

### 阶段 4：受控动作

每次只开放一个写工具，先离线评测和内部灰度，再开放给小流量用户。不要一次暴露取消、退款、购物车和支付等全部能力。

## 13. 首期明确不做

- 不做可自行分解任意目标的自由多 Agent；
- 不让 Agent 直接访问 Mapper、数据库或任意内部 URL；
- 不让模型自主退款、支付、补偿或改订单；
- 不使用未经审核的历史客服对话直接回答事实；
- 不把模型“置信度”当作权限或事实正确性的唯一判断；
- 不把现有广播 WebSocket 直接改造成客服聊天；
- 不为接入 AI 立即重写整个交易系统；
- 不在缺少评测集、人工接收方和一键停用能力时直接全量上线。

## 14. 实施前需要确认的业务决策

1. 人工客服由谁接收，服务时段和超时承诺是什么？
2. 当前真实的配送、退款、取消、食品安全和过敏原规则在哪里维护？
3. 是否允许把脱敏后的用户问题、订单必要字段发送到第三方云模型，允许的地域和保留策略是什么？
4. 首期只覆盖 `sky-web-user`，还是同时覆盖 `mp-weixin`？
5. 模型月预算、预期并发和可接受首字延迟是多少？
6. P1 最先开放哪一个确认后执行的动作？建议从“催单”或“加入购物车”开始，而不是退款/支付。
